# 범용 개발 문제해결 행동양식

이 문서는 특정 기능이나 프로젝트에 한정하지 않고, 이후 코딩·하드웨어/펌웨어·시뮬레이션·제품 개발 작업에 공통 적용한다.

## 기본 원칙

1. **증상을 먼저 정의한다.**
   - 사용자가 관찰한 현상을 임의로 기술적 원인으로 재해석하지 않는다.
   - 원래 증상을 해결 완료의 기준으로 유지한다.

2. **최소 재현 조건을 만든다.**
   - 복잡한 전체 시스템보다 문제를 가장 작게 재현하는 입력·조건을 찾는다.
   - 정상 사례와 비정상 사례를 함께 확보한다.

3. **추측하지 말고 현재 실제 상태를 확인한다.**
   - 현재 브랜치/커밋, 실제 코드, 데이터 구조, 실행 경로, 설정을 확인한다.
   - 과거 구현이나 기억을 현재 상태로 간주하지 않는다.

4. **요구사항과 불변조건을 먼저 확인한다.**
   - 수정 과정에서 기존에 합의한 규칙이 깨지지 않는지 확인한다.
   - 기능 요구사항과 구현 세부사항을 구분한다.

5. **구현보다 모델을 먼저 검증한다.**
   - 데이터 모델, 시간축, 상태 모델, 물리적 가정, 시스템 경계를 먼저 검증한다.
   - 잘못된 모델을 더 정확하게 구현하는 상황을 피한다.

6. **입력에서 실제 결과까지 실행 흐름을 추적한다.**
   - 입력 → 파싱 → 데이터 변환 → 상태 → 알고리즘 → 출력/하드웨어/오디오/배포 결과까지 실제 경로를 따라간다.
   - 필요한 경우 시간순 이벤트나 상태표로 펼친다.

7. **원인 후보를 계층별로 분리한다.**
   - 요구사항/UX → 데이터 모델 → 상태/로직 → 알고리즘 → 플랫폼/API → 성능/타이밍 → 배포/환경 순으로 검토한다.
   - 익숙한 하위 기술 문제를 먼저 고치는 식의 성급한 수정을 피한다.

8. **가설은 증거로 검증한다.**
   - “아마 이것 때문”에서 멈추지 않는다.
   - 각 가설이 실제 실행 결과에서 맞는지/틀리는지 확인한다.

9. **최소한의 원인 단위로 수정한다.**
   - 여러 원인을 동시에 바꾸지 않는다.
   - 가능하면 한 가설 → 한 수정 → 한 검증의 흐름을 유지한다.

10. **정상·경계·회귀 테스트를 모두 한다.**
    - 기본 동작뿐 아니라 최소/최대/경계값, 전환, 반복, pause/resume, 잘못된 입력 등 관련 edge case를 확인한다.
    - 기존에 정상 작동하던 기능의 회귀도 확인한다.

11. **빌드 성공과 문제 해결을 구분한다.**
    - 코드 수정 → build/CI → 배포 → 실제 환경 → 원래 증상 재현 테스트까지 확인한다.
    - 빌드가 성공했다고 기능이 해결됐다고 선언하지 않는다.

12. **실패하면 로그와 실제 결과부터 본다.**
    - Actions/build/runtime 실패 시 정확한 로그와 실패 지점을 확인한 뒤 수정한다.
    - 추측으로 연속 수정하지 않는다.

13. **‘해결’의 기준은 실제 재현 조건에서 증상이 사라진 것이다.**
    - “코드를 고쳤다”가 완료 기준이 아니다.
    - 원래 문제가 발생하던 조건에서 정상 동작하는 것을 확인해야 한다.

14. **왜 해결됐는지 설명할 수 있어야 한다.**
    - 최종 상태뿐 아니라 근본 원인, 수정 내용, 검증 방법을 설명할 수 있어야 한다.

15. **실패와 성공을 다음 작업에 반영한다.**
    - 문제 원인, 초기 오판, 유효했던 검증 방법, 피해야 할 접근, 결정 이유를 기록한다.
    - 같은 실수를 다른 프로젝트에서 반복하지 않도록 범용 원칙으로 승격한다.

## 표준 문제해결 순서

증상 정의 → 최소 재현 → 현재 실제 상태 확인 → 요구사항/불변조건 확인 → 데이터/시스템 모델 검증 → 실행 흐름 추적 → 원인 후보 계층화 → 가설별 증거 확인 → 최소 수정 → 정상/경계/회귀 테스트 → Build/CI/배포 확인 → 실제 환경 재현 테스트 → 해결 원인 확인 → 결정·실패 로그 기록

## 이번 Chords 리듬 문제에서 얻은 핵심 교훈

1 / 4 1 문제에서 처음에는 setTimeout/Web Audio timing과 voice release를 먼저 의심했다. 실제 근본 문제는 rhythm pattern을 chord마다 0번부터 다시 시작하는 모델이었다. /가 bar 경계를 의미하고 rhythm은 bar timeline을 따라가야 한다는 상위 모델을 먼저 검증했어야 했다.

따라서 앞으로는 ‘소리가 정확히 언제 나는가’보다 먼저 ‘왜 그 이벤트가 그 시점에 발생하도록 모델링되어 있는가’를 확인한다.

이 원칙은 Chords에만 적용하지 않고 모든 개발·연구·제품 작업에 공통 적용한다.
